# 远程通道策略（Remote Channel Policy）

> 生效日期：2026-08-29（Asia/Shanghai）
> 适用范围：全部五角色（协调 PM / 后端评审 / 后端实现 / 前端评审 / 前端实现）在本仓库与代码仓库的**一切远端操作**（传输、核验、PR、状态同步）
> 来源：grilling 讨论定案（通道优先级 + 代理动态开关的逐操作阶梯 + 全断降级）
> 关联：`AGENTS.md` 规则 9、`docs/agents/verification-workflow.md` §2、全局规范 v2.1 第 17 条、规则 8（敏感信息）

## 1. 背景与原则

本机网络环境下 GitHub 直连不稳定（时好时坏），本地代理（端口 7892）亦非常开——**代理状态是动态的**，任何"探测一次、会话沿用"的假设都会失效（代理中途关闭导致 `proxyconnect` 类失败、中途开启使直连恢复）。因此本策略的三大原则：

1. **无会话级状态假设**：每次远端操作都是一次独立尝试，失败后按失败类型分流（不盲信上次结论）。
2. **代理配置永不持久**：代理仅以**单命令作用域**临时注入（命令前缀环境变量），用完即逝；禁止写入会话环境、禁止写入任何 git 配置（全局规范禁改全局 git 配置）。
3. **远端不可用不阻塞本地、不豁免核验**：通道全断时本地工作照常（commit 留痕），远端操作显式登记 pending，恢复后优先补推与补核验；**未核验不声称生效**。

## 2. 通道优先级与逐操作阶梯

每次远端操作按下述阶梯执行（MCP 与 gh API 为默认优先通道——实时、结构化、不受本地 git 传输层影响）：

| 步骤 | 动作 | 说明 |
| --- | --- | --- |
| 1 | **原样尝试** | MCP 工具或 gh API（当前环境，不预设代理）；本地 git 操作（commit/log/status/diff）无网络依赖，照常执行、不适用本阶梯 |
| 2 | 失败 → **按错误类型分流** | 见 §3 分流表；禁止同参数盲目重试超过 3 次（全局规范第 6 条） |
| 3 | 成功 → **乐观缓存** | 本次可用配置（直连/代理）作为下次操作的默认尝试，减少探测开销；**一旦失败立即作废缓存**，重新走阶梯 |
| 4 | 全部不通 → **排队登记** | 按 §5 登记 pending，本地工作继续 |

## 3. 失败类型分流表

| 失败特征（示例） | 病因 | 动作 | 命令样例 |
| --- | --- | --- | --- |
| `proxyconnect tcp: EOF`、proxy refused | **环境残留失效代理变量**（代理曾开已关，HTTPS_PROXY 等残留） | **剥离代理变量重试**（GitHub 直连偶尔可通） | `env -u HTTPS_PROXY -u HTTP_PROXY gh api ...`；git：`git -c http.proxy= -c https.proxy= fetch origin` |
| 连接超时 / `SSL/TLS handshake failed` / 无法解析 | **无代理且直连被阻**（代理未开、无残留变量） | **先探测 7892**（下表）；监听中 → 单命令注入代理重试；未监听 → 排队登记 | 探测：`curl -x http://127.0.0.1:7892 -sS -o /dev/null -w "%{http_code}" --max-time 5 https://api.github.com`（返回 200/401/403 均视为代理可用）；注入：`HTTPS_PROXY=http://127.0.0.1:7892 gh api ...` |
| 401/403/422/404（HTTP 层） | **非网络问题**（认证/权限/参数/资源） | 按常规错误处理，不走本阶梯 | — |

> MCP 工具同样受进程环境代理变量影响（曾实证 `proxyconnect` 失败）；MCP 失败时按同表分流（剥离变量后经 gh/git 重试，MCP 本身无环境变量注入手段时以 gh/git 为准）。

## 4. 代理临时配置规范

- **仅单命令作用域**：`HTTPS_PROXY=http://127.0.0.1:7892 <命令>` 前缀形式；**禁止** `export` 持久化到会话、**禁止** `git config --global` / 仓库级 `http.proxy` 写入。
- 探测先行：注入前先 curl 探测（§3），探测不通直接排队登记，不做无效配置。
- gh CLI 认证与代理：gh token 经 keyring，代理仅影响传输层；注入后 gh 认证不受影响。
- **规则 8**：代理端口（7892）为本机配置可写入文档；代理订阅地址、节点、凭据等**绝不落盘**。

## 5. 排队登记与恢复补推（全断降级）

1. **触发**：阶梯走完（原样/剥离/探测注入均失败）仍无法完成远端操作。
2. **本地不阻塞**：本地工作照常——commit 留痕、文件落盘、文档撰写全部继续；仅"远端可见性"缺失。
3. **登记义务**：显式登记 pending 项，**最低字段**：操作类型（push/核验/PR/状态同步）+ 目标（分支/文件路径/PR 号）+ 涉及 SHA + 登记时间。登记位置：当前任务的状态文件 `lastAction`（或角色状态文件对应字段）/ 回执与交付物说明文字；**零新结构**（不新增清单文件）。
4. **恢复补推**：通道恢复（下次会话探测成功 / 代理开启）后，**优先补推与补核验** pending 项；补推顺序按登记时间。
5. **核验纪律**：pending 未补推/未核验期间，相关声称一律维持「未生效」口径（不得口头声称"已合入/已签署"）；补推核验完成后更新状态并按规则 9 补四字段通知。
6. **失败不豁免**：远端不可用**不构成**跳过核验、跳过回执、或降低交付标准的理由。

## 6. 乐观缓存（补充说明）

- 缓存内容：最近一次成功的通道配置（MCP 直连 / gh 直连 / 7892 代理）。
- 生命周期：**成功即续用，失败即作废**；跨会话不保留。
- 作用：减少每次操作的探测开销；代理动态开关场景下，最多损失一次失败尝试。

## 7. 各角色要点

| 角色 | 适用要点 |
| --- | --- |
| 全部角色 | 本策略适用于一切远端操作（push/核验/PR/状态文件同步）；回执与状态文件中涉及通道全断的，须按 §5 登记 pending 并在恢复后补推 |
| 协调 PM | 派发/验收链路遇通道全断时，在 `status/pm.json` lastAction 登记 pending；恢复后优先补推并同步快照链 |
| 后端/前端评审 | 签署与人链核验遇通道全断时，pending 登记；核验完成前不签"已核验远端" |
| 后端/前端实现 | 实施推送遇全断时：本地 commit 留痕 + pending 登记；恢复后补推并按规则 9 补四字段通知 |

## 8. 与既有治理的衔接

- `AGENTS.md` 规则 9：核验动作的通道表述更新为引用本策略（MCP/gh 优先，git fetch 兜底）。
- `docs/agents/verification-workflow.md` §2：R1/R2 判据的通道表述同步更新。
- 全局规范 v2.1 第 17 条：本策略为项目级细化（GitHub 直连不稳定为既定事实，项目默认 MCP/gh 优先）。
- git 安全铁律不变：本策略不涉及任何历史改写/强推/删分支授权；代理配置不触碰 git 配置文件。

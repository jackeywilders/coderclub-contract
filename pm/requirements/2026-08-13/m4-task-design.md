# M4 任务设计与 Gate 4 发布门禁（设计规格）

> **设计角色：** PM / 跨项目协调 Codex
>
> **设计日期：** 2026-08-13
>
> **设计状态：** 已获用户批准（2026-08-13，分节确认）
>
> **定位：** 本文件是 M4（Gate 2 后端安全与质量收口）的唯一 PM 任务设计入口与 Gate 4 发布门禁设计。后续每项任务的任务书、回执与验收均引用本文件。

## 1. 背景与目标

Gate 0（G0-01~06）与 Gate 1（G1-01~05）已全部验收通过并正式关闭（2026-08-13，见 `pm/reviews/2026-08-13/g1-04-close-acceptance.md`）。PM 审查记录 PM-007 指出：**M4 只是报告中的集合，不具备负责人、依赖、验收标准和停止条件**。本设计将 M4 转化为可执行、可验收、可追溯的 PM 任务清单，并建立正式的 Gate 4 发布门禁，解决发布验收无结构、无授权链的问题。

## 2. 范围与边界（已确认决策）

| 维度 | 决策 |
| --- | --- |
| M4 边界 | **仅后端收口**（Gate 2）；前端正式联调为独立 Gate 3，在 M4 后启动 |
| 优先级 | 6 项任务**全部必须**，均为发布前置硬性条件，无降级项 |
| 发布验收 | 设计为正式 **Gate 4（发布门禁）** |
| 执行模型 | **逐项独立**：每项任务书 → Claude Code 后端执行 → Backend Codex 复核 → PM 验收关闭 |
| 装饰字段 | 纳入 M4 第 6 项（M4-06），先提案后实施 |

不在本设计范围内：前端业务实现（Gate 3）、实际部署动作（由用户/运维执行）、`api/` 快照的未批准变更。

## 3. M4 任务清单（六项）

### M4-01 细粒度角色/权限矩阵

- **背景**：关闭 `G1-02-FINE-GRAINED-PERMISSION`（backend openItem，severity medium）。Auth 管理用户已覆盖 `admin_user` 角色与 403 回归；Auth Role/Permission 与 Subject 尚未配置细粒度角色/权限矩阵。
- **目标**：明确普通用户与管理员对 Subject、Auth 管理端点的 401/403 行为并实施。
- **范围**：角色/权限数据与配置、Subject 管理端点鉴权注解与 `@SaCheckPermission` 类策略、403 响应一致性（HTTP 403 + 业务 code + 统一响应体，对齐 G1-02 语义）。
- **验收标准**：
  1. 权限矩阵文档（端点 × 角色 × 行为，逐项明确匿名/登录/角色/权限）
  2. 匿名/普通用户/管理员三态回归测试（401/403 断言，对齐 `SubjectContractTest` 风格）
  3. 既有测试全绿（infra/domain/controller 契约测试）
- **回执要求**：提交哈希、矩阵文档路径、三态测试命令与输出、OpenAPI 是否变化（如变化走提案流程）。
- **依赖**：无，可最先执行。

### M4-02 OSS 访问控制

- **背景**：M3 已实现 OSS 真实上传与统一 400；「接口可用但默认匿名」的不确定性待去除。
- **目标**：明确 OSS 上传、URL 查询、调试端点的开放策略与鉴权要求。
- **范围**：OSS 端点鉴权策略（登录/角色要求）、调试端点开关策略、OpenAPI 与运行时一致。
- **验收标准**：
  1. OSS 端点策略文档（上传/查询/调试逐项明确）
  2. 鉴权测试（未登录/登录态/越权）通过
  3. OpenAPI 与运行时行为一致（差异须经提案确认）
- **回执要求**：提交哈希、策略文档路径、测试命令与输出、端点清单。
- **依赖**：无，可与 M4-01 并行。

### M4-03 凭据与环境收口

- **背景**：历史文档与脚本可能存在明文凭据；启动脚本已由 `7c3ac66` 改为先安装再运行；Nacos/环境变量优先级与端口策略需统一记录。
- **目标**：清理代码与脚本侧明文凭据，统一配置读取优先级，记录端口标准策略。
- **范围**：
  - 代码侧（Claude Code 后端职责）：启动脚本/配置文件明文密码清理、统一 Nacos/环境变量优先级、<subject-port>/<subject-alt-port> 与 <mysql-probe-port>/<mysql-port> 端口策略文档
  - 运维侧（用户/运维职责，交接仓库只记录结果）：历史暴露凭据的轮换操作
- **验收标准**：
  1. 脚本与配置无明文凭据（grep 核验 + 提交哈希）
  2. 配置优先级文档（Nacos → 环境变量 → 本地默认）
  3. 端口策略文档（标准端口与用途）
  4. 凭据轮换完成记录（运维侧，由用户提供，PM 记录）
- **回执要求**：提交哈希、grep 核验命令与输出、文档路径、轮换记录引用。
- **依赖**：无，可与 M4-01/02 并行。

### M4-04 测试质量门禁

- **背景**：覆盖率基线、集成测试方案、CI/CD 执行命令与失败处理缺失。
- **目标**：建立可重复的质量门禁：覆盖率基线、集成测试方案、CI/CD（或等价本地流程）。
- **范围**：覆盖率基线值与报告、集成测试方案（服务间链路，参考 M3 联调记录）、CI/CD 执行命令与失败处理文档。
- **验收标准**：
  1. 覆盖率报告达基线：基线值与达成目标在 M4-04 任务书中明确（先实测当前模块覆盖率作为基线，再约定目标值；建议模块级不低于实测基线且不少于 60%，最终以任务书约定为准）
  2. 集成测试方案文档（场景、命令、环境）
  3. CI/CD 执行命令与失败处理文档；**无外部 CI 环境时，以「本地可重复命令 + 文档化」为最小可验收形式**，不硬性要求接入外部 CI
- **回执要求**：提交哈希、覆盖率报告、命令与输出、CI/CD 文档路径。
- **依赖**：建议在 M4-01/02/05 完成后执行（作为最终质量基线）。

### M4-05 非法请求体处理

- **背景**：非法 UTF-8 等异常请求体的归类与异常映射未确认。
- **目标**：确认非法 UTF-8 归类 400，补齐异常映射测试。
- **范围**：异常映射（全局异常处理器）、非法请求体行为确认与测试。
- **验收标准**：
  1. 非法 UTF-8/畸形 JSON 请求实测返回 400（原始请求与响应记录）
  2. 异常映射测试通过
  3. 既有测试全绿
- **回执要求**：提交哈希、实测请求/响应、测试命令与输出。
- **依赖**：无。

### M4-06 装饰字段收敛（G1-04 遗留）

- **背景**：`SubjectInfoDTO` 列表项携带快照未声明的装饰性 `pageNo`/`pageSize` 字段（见 `pm/reviews/2026-08-13/g1-04-close-acceptance.md` 记录事项 3）。
- **目标**：收敛装饰字段，消除快照与运行时响应差异。
- **流程**（必须先提案后实施）：
  1. `proposals/backend/<日期>/m4-06-decorative-fields-<方案>.md`：评估「声明进契约」或「从运行时移除」两案，含兼容性影响
  2. PM 确认方案
  3. Claude Code 后端实施 + 测试
  4. 如涉及契约声明：同步快照（源 SHA-256/快照 SHA-256 全链更新）
- **验收标准**：
  1. 提案获 PM 批准（含选定方案）
  2. 实施提交 + 测试全绿
  3. 快照/基线一致（如涉契约变更）
- **回执要求**：提案编号、PM 确认记录、提交哈希、测试输出、快照哈希（如变化）。
- **依赖**：提案流程独立，可与任意项并行。

## 4. 执行与验收流程（沿用 G1-04 模型）

1. **PM 任务书**：每项启动时写 `pm/requirements/<日期>/m4-0X-<名称>-task.md`，引用本设计文档对应章节，明确关闭条件。
2. **Claude Code 后端执行**：实现 + 测试 + 回执 `handoff/backend-to-frontend/<日期>/m4-0X-...-report.md`（来源/分支/提交哈希、原始证据、已知限制、声明：未改 `api/` 快照与 `status/sync-manifest.json`、未伪造输出）。
3. **Backend Codex 复核**：工作底稿 `designs/backend/<日期>/m4-0X-...-review-workpaper.md` + 独立复验 + 签署。
4. **PM 验收关闭**：`pm/reviews/<日期>/m4-0X-close-acceptance.md` + 更新 `status/backend.json`（如涉）与 `status/pm.json`。
5. **执行边界**：
   - M4-03 凭据轮换属运维动作：Claude Code 后端只做代码侧，轮换由用户/运维执行并提供完成记录。
   - M4-04 无外部 CI 时不做硬性 CI 集成，以「本地可重复命令 + 文档化」验收。

**建议执行顺序**：M4-01 → M4-02/M4-03（并行）→ M4-05 → M4-04（收尾）→ M4-06 全程独立并行。

### 5.3 授权链

| 角色 | 权限 |
| --- | --- |
| Claude Code 后端/前端 | 不得修改 `releaseStatus` / `finalReleaseStatus` |
| Backend/Frontend Codex | 不得修改（仅可记录建议） |
| PM | 在**用户明确授权**后批准 `releaseStatus=published`（开发契约发布）与 `finalReleaseStatus=published`（最终发布）；两者分别记录授权人、日期、证据引用 |
| 用户 | 唯一授权来源；部署动作由用户/运维执行（交接仓库不设计部署 SOP） |

### 5.4 状态变更规则

- Gate 4 验收通过且用户授权后，PM 更新 `status/sync-manifest.json` 的 `releaseStatus` / `finalReleaseStatus` 为 `published`，并同步 `status/pm.json`（`releaseReady=true`）。
- 变更必须伴随 `pm/reviews/<日期>/release-acceptance.md`（发布验收记录，含检查清单逐项核对与授权记录）与 `pm/roadmap/2026-08-10/pm-coordination-roadmap.md` 的 Gate 4 状态更新。
- 发布后：若存在契约变更，`api/` 快照仅在对应 `proposals/` 获 PM 确认后更新；前端消费基线复核按 Gate 3 流程。

## 7. 风险与已知限制

1. **CI/CD 环境未知**：M4-04 不硬性要求外部 CI，以「本地可重复命令 + 文档化」为最小验收；若环境具备 CI 能力，在任务书中补充接入要求。
2. **凭据轮换依赖用户/运维**：M4-03 的轮换动作不在后端执行职责内，完成记录由用户提供；若轮换不可行，须 PM 书面例外（沿用 roadmap M4 P0/P1 例外机制，但本设计已确认 6 项全部必须，例外仅限执行方式而非完成）。
3. **M4-06 可能触发契约变更**：若选定「声明进契约」方案，将影响 `api/` 快照与前端基线，需走完整提案与快照同步流程；若选「运行时移除」，需确认前端无依赖该字段的消费（可在 Gate 3 前完成）。
4. **权限矩阵涉及存量数据配置**：M4-01 可能需要 Auth 角色/权限存量数据调整，属代码 + 数据双重改动，验收时需区分代码提交与数据配置记录。

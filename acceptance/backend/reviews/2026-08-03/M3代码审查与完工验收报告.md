## 1. 审查结论

**M3 当前结论：有条件通过，不建议按“全部门禁无条件通过”收口。**

Auth、OSS、OpenAPI、分类树、分页响应和现有自动化测试均达到计划要求；但以下 2 项 P1 问题影响 M3 设计中“基础鉴权闭环”和“真实跨服务联调”的完整性：

1. `AuthUserFeignClient` 没有任何实际调用方，Token 与 `X-Trace-Id` 的真实 Subject → Auth Feign 链路没有发生，当前只有拦截器单测证据。
2. Subject 的正式写接口和现有题目 CRUD 入口仍未统一增加基础登录校验，未登录请求可以绕过 M3 新增的 8 个受保护端点直接写入或修改数据。

在补齐真实 Feign 调用链、或由项目负责人正式批准将该项从 M3 门禁移交 M4，并明确 Subject 写接口的鉴权范围后，才能将结论改为“通过”。

## 2. 必须整改项

### [P1] 真实 Feign 透传没有被验证，完工报告不应标记该门禁为通过

**证据：**

- 设计文档将“Subject → Auth Feign 调用能够透传 Token 和 `X-Trace-Id`”列为运行验收标准。
- `AuthUserFeignClient` 仅在 [`AuthUserFeignClient.java:9`](../../coder-club-subject/coder-club-subject-api/src/main/java/com/jackey/req/AuthUserFeignClient.java:9) 声明，仓库搜索结果没有任何 `getUserInfo()` 调用方。
- [`FeignConfig.java:21`](../../coder-club-subject/coder-club-subject-app/coder-club-subject-app-controller/src/main/java/com/jackey/subject/app/config/FeignConfig.java:21) 的拦截器单测只能证明模板拦截行为，不能证明 Feign 编码、服务发现、远端 Auth 校验和跨服务日志链路。
- 完工报告在“Token 透传”一行同时写明“真实 Feign 调用链移交 M4”，却仍将该门禁标记为“✅ 通过”，结论不一致。

**影响：** 当前没有证据证明正式运行时会把原始 Token 和 `X-Trace-Id` 送达 Auth，也没有证据证明 Auth 返回的 `ResponseResult<UserLoginInfoVO>` 能被 Feign 调用方正确解析。

**整改要求：**

- 在 Subject 的实际业务路径中接入 `AuthUserFeignClient`，用真实请求验证 Header 透传、Auth 远端校验和响应解析；或
- 正式批准将该门禁从 M3 移交 M4，并把 M3 完工报告中的状态改为“拦截器单测通过，真实 Feign 链路未验证”。

### [P1] Subject 正式写接口缺少基础登录校验

**证据：**

- M3 计划步骤要求 Subject 的查询和写入端点增加 `@SaCheckLogin`。
- 正式端点表包含分类新增和标签新增，但 [`SubjectCategoryController.java:42`](../../coder-club-subject/coder-club-subject-app/coder-club-subject-app-controller/src/main/java/com/jackey/subject/app/controller/SubjectCategoryController.java:42) 的 `POST /subject/category/add` 没有 `@SaCheckLogin`。
- [`SubjectLabelController.java:57`](../../coder-club-subject/coder-club-subject-app/coder-club-subject-app-controller/src/main/java/com/jackey/subject/app/controller/SubjectLabelController.java:57) 的 `POST /subject/label/add` 没有 `@SaCheckLogin`。
- 题目 CRUD 入口 [`SubjectController.java:39`](../../coder-club-subject/coder-club-subject-app/coder-club-subject-app-controller/src/main/java/com/jackey/subject/app/controller/SubjectController.java:39)、[`SubjectController.java:56`](../../coder-club-subject/coder-club-subject-app/coder-club-subject-app-controller/src/main/java/com/jackey/subject/app/controller/SubjectController.java:56)、[`SubjectController.java:69`](../../coder-club-subject/coder-club-subject-app/coder-club-subject-app-controller/src/main/java/com/jackey/subject/app/controller/SubjectController.java:69) 也没有基础登录校验。
- `SubjectContractTest` 只验证了 8 个新增正式端点的无登录 401，没有覆盖上述写入口。

**影响：** 未登录客户端仍可直接新增、修改或删除题库数据。OpenAPI 当前将这些接口标为“匿名访问，M4 前不设防”，这与“基础登录校验”目标存在边界冲突，也使“Subject 未登录访问受保护接口”的验收范围不完整。

**整改要求：**

- 至少为 M3 正式的分类新增、标签新增以及题目写接口增加 `@SaCheckLogin`，补充每个接口的 401 回归测试；或
- 由项目负责人明确批准这些接口全部移交 M4，并同步修改 M3 设计、开发计划、OpenAPI 和完工报告，不能继续将“Subject 基础鉴权”写成已完整完成。

## 3. 建议改进项

### [P2] Subject 成功路径测试覆盖不足

当前 `SubjectContractTest` 的 HTTP 层主要验证无登录 401，分类树、标签列表和分页的成功场景部分通过直接调用 Controller 完成。缺少对正式 `GET`、`PUT`、`DELETE` 请求的登录成功路径、请求参数绑定和 JSON 响应结构的完整 MockMvc 验证。建议在修复 P1 时补充至少一组带登录态的成功请求测试，防止方法映射存在但真实 HTTP 绑定失败。

### [P2] Feign 客户端契约类型没有与 Auth 响应模型统一

[`AuthUserFeignClient.java:12`](../../coder-club-subject/coder-club-subject-api/src/main/java/com/jackey/req/AuthUserFeignClient.java:12) 当前声明返回 `Map<String, Object>`，而 Auth 用户信息接口实际返回 `ResponseResult<UserLoginInfoVO>`。在没有调用方时尚未产生运行时故障，但后续接入时容易出现 `data` 层级解析错误。建议 M4 接入真实调用方时改用共享的响应模型或明确的 Feign DTO，并补充反序列化测试。

### [P2] 安全凭据仍存在历史暴露风险

联调记录已经说明 Redis 密码改为环境变量注入，但 Nacos 等凭据仍在启动脚本历史中出现。该问题属于 M4 配置安全收口，不阻塞本次代码契约验收，但应在凭据轮换后清理历史暴露面。

Parameter 0 of constructor in com.jackey.oss.service.FileService required a single bean, but 3 were found:

## 7. X-Trace-Id 一致性验证

验证方法：客户端向 Auth 与 Subject 发送**同一** `X-Trace-Id`，检查两服务日志均归属同一链路值。

| 发送的 X-Trace-Id | Auth 日志命中 | Subject 日志命中 |
|---|---|---|
| `0123456789abcdef` | 3 行（GlobalExceptionHandler 异常/INFO/WARN 各 1，均带 `[0123456789abcdef]`） | 54 行（MyDruidInterceptor / mybatis-flex-sql 等） |
| `deadbeef01234567` | 1 行（WARN `[参数校验异常] [不能为空]`；该 WARN 出自 Auth 侧 GlobalExceptionHandler，与 §6.4 由 OSS 返回的 400 不同源） | 2 行 |
| `abcdef0123456789` | 0 行（Auth 成功请求无 INFO 日志输出，符合现有日志策略） | 2 行（首轮数据，结论一致） |

结论：

- 两服务均按统一 pattern 将 `%X{traceId}`（TraceIdFilter 设置的 MDC 值）写入日志；**客户端传入的同一 X-Trace-Id 在两侧日志中归属一致**。
- 401 请求在两侧均不产生日志（安全场景静默拒绝，符合预期）。
- Subject 侧通过 MyDruidInterceptor 输出 SQL 日志并携带 traceId，具备跨调用回溯能力。

## 10. 本次联调发现的问题

### 10.1 【已修复】OSS 服务无法启动：FileService 多 Bean 歧义（代码缺陷）

首轮联调发现：`FileService(StorageAdapter)` 注入存在 3 个候选 Bean（`aliStorageAdapter`/`minioStorageAdapter`/`storageService`），任何环境（含 CI/生产）启动 OSS 都会失败（§4.3）。
**已在本轮修复**：`StorageConfig.storageService` 标注 `@Primary`（提交 `fix(oss)`），OSS 启动成功并完成上传与 400 统一异常验证（§4.3/§5/§6.4）。

### 10.2 【环境】Subject 端口 <subject-port> 本机不可用

本机 `netsh interface ipv4 show excludedportrange protocol=tcp` 显示 **2911-3010 被系统动态保留**（Hyper-V/WSL2/WinNAT），<subject-port> 无法绑定（bind 报"以一种访问权限不允许的方式做了一个访问套接字的尝试"）。联调改用 `SERVER_PORT=<subject-alt-port>`。**与代码无关，不影响其他环境。**

### 10.3 【环境】MySQL 实际端口 <mysql-port>（控制者探测 <mysql-probe-port> 超时）

Nacos 配置的 JDBC URL 使用 <mysql-port>，本机可达。这是本次联调得以真实执行的原因。

### 10.4 【观察】非法 UTF-8 请求体返回 500 而非 400

客户端以非 UTF-8（GBK）字节发送 JSON 时，Jackson 解析抛 `StreamReadException`，被 `GlobalExceptionHandler` 统一兜底为 `{"code":500,"message":"系统繁忙,请稍候再试","success":false}`。
建议 M4 评审将请求体解析类异常（`HttpMessageNotReadableException`）映射为 400，与统一参数校验异常对齐。本次触发源为 Git Bash curl 的本地码页编码，属客户端行为，但服务端对畸形请求体返回 500 值得评审。

## B.4 如实记录的两点观察（非本修复范围）
